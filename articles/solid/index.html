SOLID Principles

Five object-oriented design principles (coined by Robert C. Martin, "Uncle Bob") that make software easier to understand, extend and maintain — and a favourite topic in Java / Spring Boot interviews.

S · Single Responsibility Principle

"A class should have only one reason to change." — i.e. it should do one job.

❌ Violation — one class doing three jobs

class User {
    private String name, email;

    public void saveToDatabase() { /* JDBC / persistence */ }   // reason to change #2
    public void sendWelcomeEmail() { /* SMTP logic */ }       // reason to change #3
}

This class changes if the data model, the database, or the email provider changes — three reasons.

✔ Fix — one responsibility each

class User {                 // just holds user data
    private String name, email;
}

class UserRepository {       // persistence only
    public void save(User u) { /* ... */ }
}

class EmailService {          // notifications only
    public void sendWelcome(User u) { /* ... */ }
}
🧠SRP = one class, one reason to change. Not "one method" — one responsibility.

O · Open/Closed Principle

"Software entities should be open for extension, but closed for modification." Add new behaviour by adding code, not editing existing, tested code.

❌ Violation — every new shape edits the calculator

class AreaCalculator {
    public double area(Object shape) {
        if (shape instanceof Circle c)      return 3.14 * c.r * c.r;
        else if (shape instanceof Rectangle r) return r.w * r.h;
        // adding Triangle? You must MODIFY this method again…
        return 0;
    }
}

✔ Fix — extend via a common abstraction

interface Shape { double area(); }

class Circle implements Shape {
    double r;
    public double area() { return Math.PI * r * r; }
}
class Rectangle implements Shape {
    double w, h;
    public double area() { return w * h; }
}

// The calculator never changes again
class AreaCalculator {
    public double area(Shape s) { return s.area(); }
}
// New shape = new class implementing Shape. Zero edits to AreaCalculator.
🧠OCP = extend without editing. New requirement → new class, not a new if.

L · Liskov Substitution Principle

"Objects of a superclass should be replaceable with objects of its subclasses without breaking the program." A subclass must honour the parent's contract.

❌ Classic violation — Square extends Rectangle

class Rectangle {
    protected int w, h;
    public void setWidth(int w)  { this.w = w; }
    public void setHeight(int h) { this.h = h; }
    public int area() { return w * h; }
}

class Square extends Rectangle {
    public void setWidth(int w)  { this.w = this.h = w; }  // forces both equal
    public void setHeight(int h) { this.w = this.h = h; }
}

// Code written against Rectangle now breaks:
void test(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;   // FAILS for Square -> area is 16!
}

A Square is-a rectangle mathematically, but it does not behave like one — so it isn't a valid subtype here.

✔ Fix — don't force a broken hierarchy

interface Shape { int area(); }
class Rectangle implements Shape { /* w, h */ }
class Square    implements Shape { /* side  */ }
// Each models its own invariants; neither breaks the other's contract.
🧠LSP = a subclass shouldn't surprise you. If it can't fully stand in for the parent, it shouldn't extend it.

I · Interface Segregation Principle

"Clients should not be forced to depend on methods they do not use." Prefer several small, focused interfaces over one fat one.

❌ Violation — a fat interface

interface Worker {
    void work();
    void eat();
}

class Robot implements Worker {
    public void work() { /* ok */ }
    public void eat()  { throw new UnsupportedOperationException(); }  // robots don't eat!
}

✔ Fix — split the interface

interface Workable { void work(); }
interface Eatable   { void eat();  }

class Human implements Workable, Eatable {
    public void work() { }
    public void eat()  { }
}
class Robot implements Workable {   // only what it actually needs
    public void work() { }
}
🧠ISP = many small interfaces > one fat one. No class should implement methods it must stub out.

D · Dependency Inversion Principle

"Depend on abstractions, not concretions. High-level modules shouldn't depend on low-level modules — both should depend on abstractions."

❌ Violation — high-level class nailed to a concrete class

class EmailSender {
    public void send(String msg) { /* ... */ }
}

class NotificationService {
    private EmailSender sender = new EmailSender();   // hard-wired!
    public void notify(String msg) { sender.send(msg); }
}
// Want SMS or push? You must rewrite NotificationService.

✔ Fix — depend on an abstraction, inject the implementation

interface MessageSender { void send(String msg); }

class EmailSender implements MessageSender { public void send(String m) { } }
class SmsSender   implements MessageSender { public void send(String m) { } }

class NotificationService {
    private final MessageSender sender;
    public NotificationService(MessageSender sender) {   // injected
        this.sender = sender;
    }
    public void notify(String msg) { sender.send(msg); }
}
Spring in one line: this is exactly what @Autowired / constructor injection does — the container supplies the concrete MessageSender, so your high-level code depends only on the interface.
🧠DIP = program to an interface, inject the details. new in a high-level class is a smell.

🎯 Tricky Interview Questions

The questions that separate "I memorised the acronym" from "I actually understand it."

Q1. Does SRP mean a class should have only one method?

No. SRP is about having a single reason to change (one responsibility / one actor it serves), not a single method. A class can have many methods as long as they all serve the same responsibility.

Q2. Isn't the Open/Closed Principle impossible — you always edit code eventually?

You can't make everything closed. OCP means: design so the parts most likely to change (e.g. adding a new shape, payment type, discount rule) can be extended via new classes/strategies, while the stable core stays untouched. It's about anticipating the axis of change, not achieving zero edits forever.

Q3. Give a real-world LSP violation you've seen.

The Square-extends-Rectangle problem (above), or a Bird superclass with fly() where Ostrich or Penguin must throw an exception. Also: an overridden method that strengthens preconditions (rejects inputs the parent accepted) or weakens postconditions breaks LSP even if it compiles fine.

Q4. SRP and ISP sound the same — what's the difference?

Both fight "doing too much," but at different levels. SRP applies to classes/modules (one reason to change). ISP applies to interfaces (don't force clients to implement methods they don't use). SRP is about cohesion of implementation; ISP is about the shape of the contract.

Q5. What's the difference between DIP, Dependency Injection (DI), and Inversion of Control (IoC)?

  • DIP — a design principle: depend on abstractions.
  • IoC — a broad concept: the framework, not your code, controls the flow/wiring.
  • DI — a concrete technique (constructor/setter/field injection) that implements IoC and helps you follow DIP.

So: Spring's IoC container uses DI so that your code can obey DIP.

Q6. How does the Spring Framework relate to SOLID?

Spring is basically SOLID in action: constructor injection → DIP; coding against interfaces + strategy beans → OCP; small @Repository/@Service beans → SRP; focused repository interfaces → ISP.

Q7. Can blindly following SOLID hurt a codebase?

Yes. Over-applying it leads to over-engineering — an explosion of tiny classes and interfaces with one implementation, indirection that hides intent, and premature abstraction. SOLID is a guide, not a law; apply it where change is likely, keep simple things simple (YAGNI).

Q8. Which SOLID principle does the Strategy pattern demonstrate?

Mainly OCP (add new strategies without touching the context) and DIP (the context depends on a strategy interface). Many GoF patterns are just SOLID principles crystallised into a reusable shape.
