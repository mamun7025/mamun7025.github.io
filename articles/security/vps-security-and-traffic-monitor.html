Security · Linux VPS

VPS Security & Traffic Monitor

A practical, step-by-step runbook to find out what is actually happening on a VPS that is being hammered by SSH scans or traffic spikes: who got in, what changed, what is exposed, where the traffic comes from — and only then how to harden it.

Investigate (read-only) Traffic & spikes Harden (makes changes)
Golden rule: collect evidence before you delete users, remove SSH keys, reboot or change configuration. Once you "clean up", the proof of what happened is gone. And never paste private keys, passwords or tokens into chats or tickets.
Example stack: Ubuntu/Debian VPS, Nginx → Tomcat (Java/Grails app) → MySQL, ~12 GB RAM. All IP addresses on this page are documentation placeholders (203.0.113.x, 198.51.100.x) — replace them with the ones from your own logs.

The target architecture

Everything you check below is measured against this picture. Anything reachable from the Internet that is not on this diagram is a finding.

Phase 0 · Prepare

Step 0 · Open a root shell, record the session and snapshot evidence

Every command below assumes a root shell. Recording the session gives you a timestamped log of everything you ran and saw.

sudo -i                                          # all following commands run as root

export IR=/root/ir-$(date +%F_%H%M)              # incident folder, e.g. /root/ir-2026-09-27_1015
mkdir -p "$IR" && cd "$IR"
script -a "$IR/session.log"                      # record this terminal (type 'exit' to stop)

Basic server facts

hostname; date; timedatectl | grep -Ei "time zone|synchronized"
uptime
uname -a
cat /etc/os-release | head -4
curl -s https://ifconfig.me; echo              # the server's public IP

Snapshot volatile state and logs (before anything rotates or changes)

cp -a /var/log/auth.log* /var/log/fail2ban.log* /var/log/nginx "$IR"/ 2>/dev/null
journalctl --since "30 days ago" -o short-iso > journal-30d.txt
last -Fai  > last.txt
lastb -Fai > lastb.txt 2>/dev/null
ps auxfww  > ps.txt
ss -tunap  > ss.txt
cp -a /root/.ssh/authorized_keys authorized_keys.root 2>/dev/null
sha256sum ./* > SHA256SUMS 2>/dev/null

Also note, from your own laptop

curl -s https://ifconfig.me; echo              # YOUR public IP — compare it with logins later
🧠Timezones matter. journalctl, last and Nginx logs may use different zones. Write down the server zone from timedatectl before correlating times.
Phase 1 · Who is on the box

Step 1 · Currently logged-in users and recent sessions

who
w                                                # also shows what each session is running
last -Fai | head -40                             # recent logins with full dates and IPs
lastb -Fai | head -20                            # recent FAILED logins

Red flags

  • A session whose source IP is not yours (compare with the IP you noted in Step 0).
  • A root session at a time you were not working.
  • Unknown usernames, or a session running wget, curl, python, nc in w.
  • last output that starts only recently (wtmp was wiped or rotated — note it).
Phase 2 · SSH access

Step 2 · List every successful SSH login

_COMM=sshd works whether the unit is called ssh or sshd, and whether /var/log/auth.log exists or not.

# date, method, user, source IP of every accepted login
journalctl _COMM=sshd --since "30 days ago" -o short-iso \
  | grep "Accepted" \
  | awk '{print $1, $5, $7, $9}' \
  | tee accepted.txt
Example output
2026-09-18T09:12:44+0000 publickey root 198.51.100.24
2026-09-19T21:03:10+0000 password  root 203.0.113.50     <-- needs explanation
2026-09-22T08:40:02+0000 publickey root 198.51.100.77

Which key was used?

For publickey logins sshd logs the key fingerprint. Match it against the keys in authorized_keys:

journalctl _COMM=sshd --since "30 days ago" | grep "Accepted publickey" | grep -oE "SHA256:[A-Za-z0-9+/]+" | sort | uniq -c
ssh-keygen -lf /root/.ssh/authorized_keys        # fingerprint + comment of each authorised key

Who owns the source IP?

whois 203.0.113.50 | grep -Ei "netname|org-name|orgname|country|descr" | head

Red flags

  • Accepted password for root from an IP you do not recognise — highest priority. A successful login does not prove a compromise, but it must be explained.
  • A login from a country/ISP where no admin lives or works.
  • A publickey login with a fingerprint that matches no key you own.
  • Logins by system/service accounts (www-data, tomcat, mysql).

Step 3 · Count failed attempts per IP

journalctl _COMM=sshd --since "7 days ago" \
  | grep -E "Failed password|Invalid user" \
  | grep -oE "from [0-9]{1,3}(\.[0-9]{1,3}){3}" \
  | awk '{print $2}' | sort | uniq -c | sort -nr | head -30
Example output
    800 203.0.113.94
    484 203.0.113.176
    450 198.51.100.209

Which usernames are they trying?

journalctl _COMM=sshd --since "7 days ago" | grep -oE "Invalid user [^ ]+" | sort | uniq -c | sort -nr | head -20
Reading it: hundreds of failures from a handful of IPs trying root, admin, test, ubuntu is normal Internet background noise. It only becomes an incident if one of them succeeds — which is exactly what the next step checks.

Step 4 · Did a brute-forcing IP ever get in?

This is the single most useful check on this page: intersect the "failed" IPs with the "accepted" IPs.

journalctl _COMM=sshd --since "30 days ago" | grep "Accepted" \
  | grep -oE "from [0-9.]+" | awk '{print $2}' | sort -u > ips-accepted.txt

journalctl _COMM=sshd --since "30 days ago" | grep -E "Failed|Invalid" \
  | grep -oE "from [0-9.]+" | awk '{print $2}' | sort -u > ips-failed.txt

comm -12 ips-accepted.txt ips-failed.txt         # IPs that failed AND later succeeded

How to read the result

ResultMeaning
EmptyGood No brute-forcer succeeded.
Only your own IPFine You mistyped a password at some point.
An IP with many failures, then Accepted passwordCritical A password was guessed. Treat the server as compromised and continue with Phase 4 carefully.
Phase 3 · Are the defences really working?

Step 5 · Effective SSH configuration

Don't just grep sshd_config. Files in sshd_config.d/ are included at the top and the first value wins, so a cloud-init file can silently re-enable passwords.

# what sshd is ACTUALLY using
sshd -T | grep -Ei "^(port|permitrootlogin|passwordauthentication|kbdinteractiveauthentication|pubkeyauthentication|permitemptypasswords|maxauthtries|allowusers|allowgroups) "

# where each setting comes from
grep -nEi "^\s*(Include|PermitRootLogin|PasswordAuthentication|KbdInteractiveAuthentication)" \
  /etc/ssh/sshd_config /etc/ssh/sshd_config.d/*.conf 2>/dev/null

Expected vs red flag

SettingGoodRed flag
permitrootloginno / prohibit-passwordyes — root password logins possible
passwordauthenticationnoyes — brute force can succeed
kbdinteractiveauthenticationnoyes — password prompt via PAM
permitemptypasswordsnoyes
pubkeyauthenticationyesno
If Step 2 showed Accepted password for root, then permitrootlogin yes + passwordauthentication yes is the root cause of the exposure, regardless of whether that particular login was you.

Step 6 · Fail2Ban: running is not the same as working

systemctl is-active fail2ban
fail2ban-client status                           # list of jails
fail2ban-client status sshd                      # failed/banned counters + banned IP list
fail2ban-client get sshd maxretry
fail2ban-client get sshd findtime
fail2ban-client get sshd bantime
fail2ban-client banned                           # all bans (fail2ban 0.11+)

# where does the jail read its log from?
fail2ban-client get sshd logpath
fail2ban-client get sshd journalmatch            # used when backend = systemd

# how many bans in total (including rotated logs)
zgrep -h " Ban " /var/log/fail2ban.log* | wc -l

Red flags

  • No sshd jail in the list — Fail2Ban is running but protecting nothing.
  • Total failed: 0 while Step 3 shows hundreds of failures — the jail is reading the wrong log. Typical on newer Ubuntu/Debian with no /var/log/auth.log: the jail needs backend = systemd (fix in Step 26).
  • The top IPs from Step 3 are still not banned.
  • bantime of a few minutes — attackers simply come back.
  • Your own IP in the banned list (add it to ignoreip).
Phase 4 · Exposure

Step 7 · What is listening, and on which address

ss -lntup
How to read the Local Address column
Local addressMeaning
127.0.0.1:8080 / [::1]:3306Private Only reachable from the server itself
0.0.0.0:8080 / *:8080 / [::]:3306Public Reachable from the Internet unless the firewall blocks it

Expected ports for this stack

PortServiceShould bind to
22SSHpublic
80 / 443Nginxpublic
8080Tomcat HTTP connector127.0.0.1
8005Tomcat shutdown port127.0.0.1 (or disabled)
8009Tomcat AJPdisabled (Ghostcat, CVE-2020-1938)
3306 / 33060MySQL / MySQL X127.0.0.1

Any port not on this list (e.g. a random high port owned by an unknown process) is a finding — note the PID and program name.

Step 8 · Firewall rules

ufw status verbose
firewall-cmd --state 2>/dev/null                 # only on RHEL-family servers
nft list ruleset | head -80

Red flags

  • Status: inactive and no other nftables/iptables rules.
  • Default: allow (incoming).
  • Rules like 8080 ALLOW Anywhere or 3306 ALLOW Anywhere.
Don't change rules yet. You're still collecting evidence; hardening comes in Phase 8.

Step 9 · Verify from the outside (the only view that counts)

Local config can lie; a scan from another machine can't. Run this from your laptop — only against your own server.

nmap -Pn -p 22,80,443,3306,8005,8009,8080,8443,33060 <VPS_IP>

curl -sI http://<VPS_IP>:8080/                  # should time out / be refused
curl -sI http://<VPS_IP>:8080/manager/html      # Tomcat manager must never be public
curl -sI https://your-domain.com/manager/html    # …also not through Nginx

Red flags

  • Anything besides 22, 80, 443 shows as open.
  • /manager/html answers with 401 or 200 from the Internet — it's exposed to password guessing and, once in, allows deploying a WAR (= remote code execution).

Step 10 · Tomcat and MySQL specifics

Tomcat

systemctl list-units --type=service | grep -i tomcat
ps -o user,pid,rss,cmd -C java                   # which user runs Tomcat? (should NOT be root)

# Tomcat base dir, taken from the running process (-Dcatalina.base=...)
TC=$(ps -o args= -C java | grep -oE 'catalina\.base=[^ ]+' | head -1 | cut -d= -f2)
echo "${TC:-not found — set TC manually, e.g. /opt/tomcat or /var/lib/tomcat9}"
grep -nE "<Connector|<Server port" "$TC"/conf/server.xml
grep -nE "<user " "$TC"/conf/tomcat-users.xml    # manager users & roles
ls "$TC"/webapps/

MySQL

ss -lntp | grep -E ":3306|:33060"
grep -R "bind-address" /etc/mysql/ 2>/dev/null
mysql -e "SELECT user, host, plugin FROM mysql.user;"

Red flags

  • Tomcat running as root — any app bug becomes full server takeover.
  • Connector without address="127.0.0.1", AJP connector enabled, shutdown port not on localhost.
  • manager/host-manager webapps deployed with weak or default passwords.
  • MySQL bind-address = 0.0.0.0, or users with host = '%' (especially root@'%').
Phase 5 · Persistence — did anyone leave a backdoor?

Step 11 · SSH keys for every user

find / -xdev \( -name authorized_keys -o -name authorized_keys2 \) 2>/dev/null \
  | while read f; do echo "== $f"; stat -c "modified: %y" "$f"; ssh-keygen -lf "$f"; done

Red flags

  • A key whose comment/fingerprint you can't attribute to a real person or deploy system.
  • A modification time close to a suspicious login from Step 2.
  • authorized_keys in service-account homes (/var/www, /opt/tomcat, /var/lib/mysql).
  • Keys prefixed with command="…" you didn't add.
Record before removing. You already copied root's file in Step 0 — copy any other suspicious file into $IR too.

Step 12 · Users, UID 0 and sudo rights

awk -F: '$3 == 0 {print "UID0:", $1}' /etc/passwd                 # only 'root' is allowed here
awk -F: '$7 !~ /(nologin|false|sync)$/ {print $1, $3, $6, $7}' /etc/passwd   # users with a real shell
awk -F: '$2 == "" {print "EMPTY PASSWORD:", $1}' /etc/shadow
ls -l --time-style=long-iso /etc/passwd /etc/shadow /etc/group /etc/sudoers
getent group sudo wheel admin
grep -RvE "^\s*(#|$)" /etc/sudoers /etc/sudoers.d/ 2>/dev/null

Red flags

  • Any UID 0 account other than root.
  • New users you didn't create, or service accounts given /bin/bash.
  • An account with an empty password.
  • NOPASSWD: ALL entries you don't recognise; recent mtime on /etc/passwd or /etc/shadow.

Step 13 · Cron jobs and systemd timers/services

# cron — system-wide and per user
cat /etc/crontab
ls -la /etc/cron.d/ /etc/cron.hourly/ /etc/cron.daily/ /etc/cron.weekly/ /etc/cron.monthly/
grep -RvE "^\s*(#|$)" /etc/cron.d/ 2>/dev/null
ls -la /var/spool/cron/crontabs/ 2>/dev/null      # one file per user that has a crontab
for u in $(cut -d: -f1 /etc/passwd); do c=$(crontab -l -u "$u" 2>/dev/null | grep -vE "^\s*(#|$)"); [ -n "$c" ] && echo "== $u" && echo "$c"; done

# systemd — enabled services, timers, recently changed unit files
systemctl list-unit-files --type=service --state=enabled
systemctl list-timers --all
find /etc/systemd /usr/lib/systemd/system /lib/systemd/system -type f -mtime -30 \
  -printf '%TY-%Tm-%Td %TH:%TM %p\n' 2>/dev/null | sort -r | head -30

Red flags

  • Entries that curl/wget something and pipe it to sh, or contain base64 blobs.
  • Jobs running binaries from /tmp, /var/tmp, /dev/shm or hidden dirs (/.x, ~/.cache/.sys).
  • Services with generic names (system-update.service, dbus-helper) that no package owns — check with dpkg -S /path/to/file.

Step 14 · Other classic hiding spots

cat /etc/ld.so.preload 2>/dev/null              # should NOT exist — used by userland rootkits
cat /etc/rc.local 2>/dev/null
ls -la /etc/profile.d/
grep -nE "curl|wget|nc |/dev/tcp|base64" /root/.bashrc /root/.profile /home/*/.bashrc 2>/dev/null

# executables in temp dirs
find /tmp /var/tmp /dev/shm -type f -perm -u+x -ls 2>/dev/null

# files changed in the last 7 days in key places
find /etc /root /opt /var/www /usr/local/bin /usr/bin -xdev -type f -mtime -7 \
  -printf '%TY-%Tm-%Td %TH:%TM %p\n' 2>/dev/null | sort -r | head -100

# modified package-owned files (Debian/Ubuntu); '5' in column 3 = content changed
dpkg --verify 2>/dev/null | grep -v " c /" | head -50

Red flags

  • /etc/ld.so.preload exists.
  • Executables in /tmp or /dev/shm.
  • Changed files in /usr/bin or /usr/sbin that no update explains (compare with Step 15's package log).
  • dpkg --verify reporting modified binaries like /usr/bin/ps, /usr/bin/ss, /usr/sbin/sshd.

Step 15 · Shell history, sudo activity, packages and web shells

# shell history (not a complete record — missing history proves nothing)
ls -la /root/.bash_history /home/*/.bash_history 2>/dev/null
tail -100 /root/.bash_history

# sudo commands
journalctl _COMM=sudo --since "30 days ago" -o short-iso | grep "COMMAND=" | tail -50

# package installs/upgrades
grep -hE " install | upgrade " /var/log/dpkg.log* 2>/dev/null | sort | tail -50
zgrep -h -A1 "^Commandline" /var/log/apt/history.log* 2>/dev/null | tail -40

# JSP web shells dropped into Tomcat
find "$TC"/webapps /var/lib/tomcat*/webapps -name "*.jsp" -mtime -30 -ls 2>/dev/null

Red flags

  • .bash_history is a symlink to /dev/null, empty, or was truncated recently.
  • Packages like masscan, nmap, tor, proxychains installed without your knowledge.
  • New .jsp files inside a deployed Grails WAR (Grails apps normally don't ship loose JSPs).
Phase 6 · Processes & network

Step 16 · Suspicious processes

ps aux --sort=-%cpu | head -15
ps aux --sort=-%mem | head -15

# binaries that were deleted after starting (a common malware trick)
ls -l /proc/*/exe 2>/dev/null | grep deleted

# processes whose executable lives in a temp or hidden dir
ls -l /proc/*/exe 2>/dev/null | grep -E "/tmp/|/var/tmp/|/dev/shm/|/\."

Red flags

  • A process pinned at ~100% CPU per core that isn't Java/MySQL — typical crypto-miners: xmrig, kdevtmpfsi, kinsing, or random names like .x, [kworker] running as a normal user.
  • Kernel-looking names in square brackets owned by a non-root user.
  • Children of Tomcat's java process running sh, bash, curl — check with ps auxf. That means code execution through the web app.

Step 17 · Outbound connections

# established connections with owning process
ss -tnp state established

# outbound only: skip connections to our own public ports and to localhost
ss -Htnp state established | awk '$3 !~ /:(22|80|443)$/ && $4 !~ /^(127\.|\[::1\])/' | sort -k4

# everything with a network socket
lsof -i -n -P | grep -v "127.0.0.1"

Red flags

  • Connections to ports 3333, 4444, 5555, 7777, 14444 (mining pools), 6667 (IRC botnets).
  • Your server connecting to many different IPs on port 22 — it's being used to brute-force others.
  • Outbound connections from www-data/tomcat processes to unknown hosts.
Phase 7 · Traffic monitor & spikes

Step 18 · Live bandwidth and connection overview

First find out whether there is a spike and on which interface, then drill into who causes it.

ip -br addr                                      # find the interface name, e.g. eth0
ip -s link show eth0                             # RX/TX byte counters since boot
ss -s                                            # socket summary: established, time-wait…

apt install -y vnstat iftop nethogs              # once
vnstat -h                                        # traffic per hour (history kept by the vnstat daemon)
vnstat -d                                        # per day
iftop -i eth0 -nNP                               # live: which remote IP uses the bandwidth
nethogs eth0                                     # live: which PROCESS uses the bandwidth
Tip: vnstat only starts collecting after it's installed. Install it now, even if the spike is over, so next time you have history.

Step 19 · Connections per client IP

# who holds the most open connections to Nginx right now
ss -Htn state established '( sport = :80 or sport = :443 )' \
  | awk '{print $4}' | sed -E 's/:[0-9]+$//; s/^\[?(::ffff:)?//; s/\]$//' \
  | sort | uniq -c | sort -nr | head -20

# SYN flood indicator: many half-open connections
ss -Htn state syn-recv | wc -l

Red flags

  • A single IP holding hundreds of connections (normal browsers use ~6–10).
  • Hundreds or thousands of syn-recv sockets.

Step 20 · Find the spike in the Nginx access log

The default "combined" log format: $1 = client IP, $4 = time, $7 = URL, $9 = status. zcat -f also reads rotated .gz files.

LOG="/var/log/nginx/access.log*"

# busiest minutes — the spike window
zcat -f $LOG | awk '{print substr($4, 2, 17)}' | sort | uniq -c | sort -nr | head -15

# requests per hour, chronological (to see the shape of the day)
zcat -f /var/log/nginx/access.log | awk '{print substr($4, 2, 14)}' | uniq -c

# status code distribution
zcat -f $LOG | awk '{print $9}' | sort | uniq -c | sort -nr

# top client IPs, top URLs, top user agents
zcat -f $LOG | awk '{print $1}' | sort | uniq -c | sort -nr | head -20
zcat -f $LOG | awk '{print $7}' | sort | uniq -c | sort -nr | head -20
zcat -f $LOG | awk -F'"' '{print $6}' | sort | uniq -c | sort -nr | head -15

Drill into one spike window

W="27/Sep/2026:14:3"                             # 14:30–14:39 on that day
zcat -f $LOG | grep "$W" | awk '{print $1}'  | sort | uniq -c | sort -nr | head -10   # who
zcat -f $LOG | grep "$W" | awk '{print $7}'  | sort | uniq -c | sort -nr | head -10   # what
zcat -f $LOG | grep "$W" | awk '{print $9}'  | sort | uniq -c | sort -nr              # result

# everything one suspicious IP did
zcat -f $LOG | grep "^203.0.113.94 " | tail -50

Attack scans and errors

zcat -f $LOG | grep -Ei "wp-admin|wp-login|xmlrpc|\.env|\.git/|phpmyadmin|cgi-bin|/manager/html|etc/passwd|\.\./|cmd=|union.*select|jndi:" | tail -50

# IPs producing the most 4xx/5xx
zcat -f $LOG | awk '$9 ~ /^[45]/ {print $1, $9}' | sort | uniq -c | sort -nr | head -20

tail -100 /var/log/nginx/error.log
Scanner noise is normal. Requests for /wp-login.php on a Grails app just return 404 and don't prove anything. What matters: did any scan request get a 200, and did anything hit /manager/html or a Log4Shell-style ${jndi:…} payload successfully?

Step 21 · Is the server itself struggling?

A "spike" users feel as slowness may be CPU, memory, disk, or the JVM — not network.

uptime                                           # load average vs. number of cores (nproc)
nproc
vmstat 1 5                                       # r = run queue, si/so = swapping, wa = IO wait
free -h
df -h; df -ih                                    # full disk or inodes breaks logging and MySQL
du -xhd1 /var/log | sort -h

# out-of-memory kills (often Tomcat or MySQL on a 12 GB box)
journalctl -k --since "7 days ago" | grep -iE "out of memory|oom-kill|killed process"

# JVM heap limit vs. actual usage
ps -o pid,rss -C java                            # RSS in KB
ps -o args= -C java | grep -oE -- "-Xm[sx][^ ]+"

# warnings and errors across the system
journalctl -p warning..alert --since "7 days ago" | tail -50
last -x reboot shutdown | head

What kind of spike is it?

SymptomLikely causeAction
One or few IPs, same URL, high req/minScraper / floodBan IP, Nginx limit_req (Step 28)
Many IPs, random URLs like .env, wp-*, mostly 404Vulnerability scannersRate limit, return 444 for known junk paths
Many IPs, real app URLs, 200s, normal user agentsReal users (campaign, traffic peak)Tune Tomcat/JVM/MySQL, cache, scale
No request spike but CPU at 100%Miner or runaway app threadBack to Step 16; jstack the JVM
High outbound traffic, few inbound requestsServer is attacking others / data exfiltrationTreat as compromise, Step 17
OOM kills in kernel logHeap/buffer sizes exceed RAMRight-size -Xmx and innodb_buffer_pool_size

Step 22 · Log request time for better spike analysis (optional)

The default Nginx format doesn't include how long a request took. Add it so slow endpoints show up in the log.

/etc/nginx/conf.d/log-format.conf
log_format timed '$remote_addr - $remote_user [$time_local] "$request" '
                 '$status $body_bytes_sent "$http_referer" "$http_user_agent" '
                 'rt=$request_time urt=$upstream_response_time';
In your server block
access_log /var/log/nginx/access.log timed;
nginx -t && systemctl reload nginx

# slowest requests: seconds + URL
awk '{for (i = NF; i > 7; i--) if ($i ~ /^rt=/) { sub("rt=", "", $i); print $i, $7 }}' \
  /var/log/nginx/access.log | sort -nr | head -20
The column positions in Step 20 stay the same, because the new fields are appended at the end.
Phase 8 · Correlate & decide

Step 23 · Build the timeline around each suspicious login

One login line means little on its own. What happened in the ±30 minutes around it tells you whether it was you or an intruder.

Accepted password for root from 203.0.113.50 at 2026-09-19 21:03
        |
        +--> Is 203.0.113.50 you / a colleague / your office VPN?   (Step 0, 2)
        +--> Did this IP brute-force before?                       (Step 4)
        +--> Commands & sudo around 21:03                          (Step 15)
        +--> Files modified 20:30 – 23:00                          (below)
        +--> authorized_keys / users / cron / systemd changed?     (Step 11–13)
        +--> New processes or outbound connections?                (Step 16–17)
# everything the system logged in the window
journalctl --since "2026-09-19 20:30" --until "2026-09-19 23:00" -o short-iso | less

# files created/modified in the window
find / -xdev -type f -newermt "2026-09-19 20:30" ! -newermt "2026-09-19 23:00" 2>/dev/null \
  | grep -vE "^/(proc|sys|run)|/var/log/journal" | head -200

# how long that session lasted
journalctl _COMM=sshd --since "2026-09-19 20:30" --until "2026-09-20 06:00" | grep -E "session (opened|closed)|Disconnected"

Verdict matrix

EvidenceVerdictNext step
All successful logins are attributable to you/your team, Steps 11–17 cleanNoisy, not compromisedHarden (Phase 9) to stop the noise and close the door.
An unexplained successful login, but nothing changed afterwardsSuspiciousRotate root password and all keys, harden, keep monitoring closely.
Brute-forcer succeeded (Step 4), or unknown keys/users/cron/services, miners, deleted binaries, ld.so.preload, web shellsCompromisedSee the box below.
If the server is compromised: a box where an attacker had root can't be trusted again, even after cleaning — rootkits can hide from the very tools you'd use to check. Keep the evidence folder, build a fresh VPS, deploy the app from source/CI (not from files copied off the old box), restore data from a backup taken before the intrusion, and rotate every secret: root and user passwords, SSH keys, MySQL passwords, the app's application.yml/datasource credentials, API tokens and TLS keys.
Phase 9 · Harden — only after evidence is collected

Step 24 · Create a sudo user with an SSH key (before touching root)

On your laptop
ssh-keygen -t ed25519 -C "mamun@laptop"          # skip if you already have a key
ssh-copy-id -i ~/.ssh/id_ed25519.pub root@<VPS_IP>
On the server (optional but recommended — a named admin instead of root)
adduser deploy
usermod -aG sudo deploy
install -d -m 700 -o deploy -g deploy /home/deploy/.ssh
cp /root/.ssh/authorized_keys /home/deploy/.ssh/ && chown deploy:deploy /home/deploy/.ssh/authorized_keys
chmod 600 /home/deploy/.ssh/authorized_keys

passwd root                                      # new, long, unique root password
From a second terminal — must work before you continue
ssh deploy@<VPS_IP> 'sudo whoami'                # expect: root

Step 25 · Disable password and root password logins

Use a drop-in file named 00-… so it's read first and wins over files like 50-cloud-init.conf.

/etc/ssh/sshd_config.d/00-hardening.conf
PermitRootLogin prohibit-password      # or 'no' if you log in as 'deploy'
PasswordAuthentication no
KbdInteractiveAuthentication no
PermitEmptyPasswords no
PubkeyAuthentication yes
MaxAuthTries 3
LoginGraceTime 30
X11Forwarding no
sshd -t                                          # syntax check — must print nothing
systemctl reload ssh                             # 'sshd' on RHEL-family
sshd -T | grep -Ei "^(permitrootlogin|passwordauthentication|kbdinteractiveauthentication) "
Keep your current session open. Open a new terminal and log in again. Only close the old session once the new login works. Verify passwords are refused: ssh -o PubkeyAuthentication=no root@<VPS_IP> must fail with Permission denied (publickey).

Step 26 · Make Fail2Ban actually ban

/etc/fail2ban/jail.local
[DEFAULT]
ignoreip = 127.0.0.1/8 ::1 <YOUR_IP>
bantime  = 1h
findtime = 10m
maxretry = 5
backend  = systemd              # reads the journal — works without /var/log/auth.log

[sshd]
enabled = true

[recidive]                      # repeat offenders: banned for a week
enabled  = true
logpath  = /var/log/fail2ban.log
backend  = auto
bantime  = 1w
findtime = 1d
maxretry = 3
fail2ban-client -t                               # test configuration
systemctl enable --now fail2ban
systemctl restart fail2ban
fail2ban-client status sshd                      # "Currently failed" should start climbing within minutes

Step 27 · Firewall: deny by default, allow 22/80/443

ufw default deny incoming
ufw default allow outgoing
ufw allow OpenSSH                                # FIRST — or you lock yourself out
ufw allow 80/tcp
ufw allow 443/tcp
ufw limit OpenSSH                                # extra: max 6 new SSH connections / 30 s per IP
ufw enable
ufw status verbose
Repeat the external nmap scan from Step 9. Only 22, 80 and 443 should be open. Many VPS providers also offer a cloud firewall in their panel — use it as a second layer.

Step 28 · Lock Tomcat and MySQL to localhost, rate-limit Nginx

Tomcat — conf/server.xml

<!-- shutdown port: localhost only (or port="-1" to disable) -->
<Server port="8005" address="127.0.0.1" shutdown="CHANGE-ME-random-string">

<!-- HTTP connector reachable only by Nginx -->
<Connector port="8080" address="127.0.0.1" protocol="HTTP/1.1"
           connectionTimeout="20000" />

<!-- AJP: remove or keep commented out -->
<!-- <Connector protocol="AJP/1.3" port="8009" ... /> -->

Also delete webapps/manager, host-manager, docs and examples if you deploy by copying the WAR, and run Tomcat as its own non-root user.

MySQL — /etc/mysql/mysql.conf.d/mysqld.cnf

[mysqld]
bind-address       = 127.0.0.1
mysqlx-bind-address = 127.0.0.1   # MySQL 8 only — remove this line on MariaDB
systemctl restart mysql
mysql -e "SELECT user, host FROM mysql.user WHERE host = '%';"   # should be empty

Nginx — basic rate limiting

http { } block, e.g. /etc/nginx/conf.d/limits.conf
limit_req_zone  $binary_remote_addr zone=perip:10m rate=10r/s;
limit_conn_zone $binary_remote_addr zone=conns:10m;
server { } block
limit_req  zone=perip burst=40 nodelay;
limit_conn conns 30;
limit_req_status 429;

# never proxy these to the app
location ~ ^/(manager|host-manager)(/|$) { return 404; }
location ~ /\.(env|git|svn|ht)           { return 404; }
nginx -t && systemctl reload nginx
Tune rate and burst to your real traffic from Step 20 — a single page load of a Grails app can request 20+ assets.

Step 29 · Automatic security updates and a daily check

apt install -y unattended-upgrades
dpkg-reconfigure -plow unattended-upgrades       # answer "Yes"
/usr/local/bin/vps-daily-check.sh
#!/usr/bin/env bash
# Daily one-page security & traffic summary
echo "== $(hostname) — $(date -Is)"
echo "-- SSH logins accepted (24h)";  journalctl _COMM=sshd --since "24 hours ago" | grep Accepted | awk '{print $1,$2,$3,$7,$9,$11}'
echo "-- SSH failures (24h)";         journalctl _COMM=sshd --since "24 hours ago" | grep -cE "Failed|Invalid"
echo "-- Fail2Ban";                   fail2ban-client status sshd | grep -E "Currently|Total"
echo "-- Public listeners";           ss -Hlnt | awk '$4 !~ /^(127\.0\.0\.1|\[::1\])/ {print $4}' | sort -u
echo "-- Top IPs in Nginx today";     grep "$(date +%d/%b/%Y)" /var/log/nginx/access.log | awk '{print $1}' | sort | uniq -c | sort -nr | head -5
echo "-- Load / memory / disk";       uptime; free -h | sed -n 2p; df -h / | tail -1
echo "-- Top CPU";                    ps aux --sort=-%cpu | sed -n 2,4p
chmod 700 /usr/local/bin/vps-daily-check.sh
echo '15 7 * * * root /usr/local/bin/vps-daily-check.sh > /var/log/vps-daily-check.log 2>&1' \
  > /etc/cron.d/vps-daily-check
🧠The script prints "Public listeners". If port 8080 or 3306 ever shows up there again, someone changed a config — you'll see it the next morning instead of months later.
