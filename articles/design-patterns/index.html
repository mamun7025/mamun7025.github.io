Creational Patterns

These deal with object creation — hiding the messy details of how instances come to life.

01 · Singleton Creational

An application has a single Configuration Manager. We don't want each layer building its own copy — everyone shares one instance.

              ┌─────────────────┐
Application ──▸│ Configuration   │
Service ─────▸│ Manager         │
Controller ───▸│ ONE object      │
              └─────────────────┘
Java
class ConfigurationManager {

    private static ConfigurationManager instance;

    private ConfigurationManager() { }

    public static ConfigurationManager getInstance() {
        if (instance == null) {
            instance = new ConfigurationManager();
        }
        return instance;
    }
}

// c1 == c2  ->  true  (same object)
ConfigurationManager c1 = ConfigurationManager.getInstance();
ConfigurationManager c2 = ConfigurationManager.getInstance();
Spring note: Spring beans are singleton-scoped by default, but that's managed by the container — it's not identical to the classic GoF singleton implementation.
🧠Singleton = only ONE instance.

02 · Factory Creational

Instead of the client calling new VisaPayment() everywhere, it asks a factory: "give me the right object for this type."

        Payment Request
              ↓
        Payment Factory
         /     |      \
      VISA   PayPal   ApplePay
Java
interface Payment { void pay(); }

class VisaPayment implements Payment {
    public void pay() { System.out.println("Paying using Visa"); }
}

class PaypalPayment implements Payment {
    public void pay() { System.out.println("Paying using PayPal"); }
}

class PaymentFactory {
    public static Payment create(String type) {
        if ("VISA".equals(type))   return new VisaPayment();
        if ("PAYPAL".equals(type)) return new PaypalPayment();
        throw new IllegalArgumentException("Unknown payment");
    }
}

// Client just asks for what it needs
Payment payment = PaymentFactory.create("VISA");
payment.pay();
🧠Factory = "Tell me what you need; I'll create it."

03 · Builder Creational

Great for objects with many optional parameters. A telescoping constructor is unreadable — a builder makes each value self-documenting.

Without builder — what does each argument mean?
User user = new User("Mamun", "mamun@email.com", 33, "Dubai", "Java", true);
With builder — readable, order-independent
User user = User.builder()
        .name("Mamun")
        .email("mamun@email.com")
        .age(33)
        .city("Dubai")
        .skill("Java")
        .active(true)
        .build();
This is exactly why you see Lombok's @Builder all over Spring Boot code.
🧠Builder = build a complex object step-by-step.
Structural Patterns

These deal with how objects and classes are connected together.

04 · Adapter Structural

Your app expects PaymentService, but a third-party bank exposes BankPaymentAPI. The interfaces don't match, so you wrap it in a translator.

Your App  →  PaymentService  →  Adapter  →  BankPaymentAPI
Java
interface PaymentService { void pay(double amount); }

// Third-party class with an incompatible method name
class BankPaymentAPI {
    public void makePayment(double amount) {
        System.out.println("Bank payment: " + amount);
    }
}

// Adapter bridges the two
class BankPaymentAdapter implements PaymentService {
    private BankPaymentAPI bankAPI = new BankPaymentAPI();
    public void pay(double amount) { bankAPI.makePayment(amount); }
}

PaymentService payment = new BankPaymentAdapter();
payment.pay(1000);
🧠Adapter = translator between incompatible interfaces.

05 · Decorator Structural

A coffee + milk + sugar + cream. Instead of a class for every combination, you wrap the base object, and each wrapper adds one behavior.

Coffee → MilkDecorator → SugarDecorator → CreamDecorator
Java (concept)
Coffee coffee = new BasicCoffee();
coffee = new MilkDecorator(coffee);
coffee = new SugarDecorator(coffee);
coffee = new CreamDecorator(coffee);
Real Java example: the I/O streams — new DataInputStream(new BufferedInputStream(inputStream)). Each wrapper adds functionality.
🧠Decorator = add behavior by wrapping the original object.

06 · Facade Structural

Making a payment touches account validation, balance, fraud checks, processing and notifications. A facade hides all of that behind one simple call.

Client
  ↓
PaymentFacade
  ↓
 ├─ AccountService
 ├─ FraudService
 ├─ PaymentService
 └─ NotificationService
Java
// Client doesn't need to know the sub-systems exist
paymentFacade.pay(amount);
🧠Facade = one simple front door to a complicated system.

07 · Proxy Structural

A security guard stands in front of the real object. The client talks to the proxy, which can authenticate, authorize, log, cache or control access before delegating.

Client  →  Proxy (guard)  →  Real Service
Spring example
@Transactional
public void transferMoney() {
    // Spring wraps this bean in a proxy that
    // opens/commits the transaction around the call
}
🧠Proxy = gatekeeper in front of the real object.
Behavioral Patterns

These deal with how objects communicate and distribute responsibilities.

08 · Strategy Behavioral

Multiple payment methods, one job: pay. Instead of a giant if/else, each algorithm becomes its own swappable strategy.

PaymentService
      ↓
   Strategy
   /   |   \
 Card PayPal Bank
Java
interface PaymentStrategy { void pay(double amount); }

class CardPayment implements PaymentStrategy {
    public void pay(double amount) { System.out.println("Card payment"); }
}

class PaymentService {
    private PaymentStrategy strategy;
    public PaymentService(PaymentStrategy strategy) { this.strategy = strategy; }
    public void pay(double amount) { strategy.pay(amount); }
}

// Inject the behavior you want
PaymentService service = new PaymentService(new CardPayment());
service.pay(1000);
🧠Strategy = same job, different ways of doing it.

09 · Chain of Responsibility Behavioral

Expense approval by level. Each handler asks "Can I approve this?" — if not, it passes the request along the chain.

Employee → Manager ($100) → Director ($1k) → VP ($10k) → CEO (>$10k)

approveExpense(5000):
  Manager  → No
  Director → No
  VP       → Yes  ✓
Java
abstract class ExpenseHandler {
    protected ExpenseHandler next;
    public void setNext(ExpenseHandler next) { this.next = next; }
    public abstract void approveExpense(double amount);
}

class Manager extends ExpenseHandler {
    public void approveExpense(double amount) {
        if (amount <= 100)      System.out.println("Manager approved: $" + amount);
        else if (next != null) next.approveExpense(amount);
    }
}
// Director (<= 1000) and VP (<= 10000) follow the same shape...

ExpenseHandler manager = new Manager(), director = new Director(), vp = new VP();
manager.setNext(director);
director.setNext(vp);
manager.approveExpense(5000);   // -> VP approved: $5000.0
Spring Boot: the same idea powers HTTP filter chains — authentication → authorization → logging → validation → controller.
🧠Chain = pass the request along until someone handles it.

10 · Observer Behavioral

An order is created → publish an event → every interested subscriber reacts. The publisher doesn't need to know who's listening. This is the heart of event-driven architecture and Kafka.

Order Created → OrderCreated event
                    ↓
     ┌───────┴──────────┴───────────┐
     ↓             ↓              ↓
   Email          SMS         Notification
Spring example
@EventListener
public void onOrderCreated(OrderCreated event) { /* react */ }
🧠Observer = one event → notify many interested parties.

11 · Template Method Behavioral

Every payment follows the same skeleton — validate, authenticate, process, notify — but the process step differs. The base class fixes the steps; subclasses fill in the variable part.

Java
abstract class Payment {
    // final = the workflow order can't be changed
    public final void process() {
        validate();
        authenticate();
        makePayment();     // <- the only step subclasses change
        notifyCustomer();
    }
    abstract void makePayment();
    void validate()      { System.out.println("Validate"); }
    void authenticate()  { System.out.println("Authenticate"); }
    void notifyCustomer(){ System.out.println("Notify"); }
}

class CardPayment extends Payment {
    void makePayment() { System.out.println("Card payment"); }
}
🧠Template Method = same steps, different implementation of some steps.

12 · Command Behavioral

A waiter takes your order but doesn't cook it. The request is packaged as a command object and handed to whoever executes it.

Client → Command → Invoker → Receiver

Useful for job queues, undo/redo, task scheduling, and message processing — anywhere you want to store, queue or replay an action.

🧠Command = turn a request/action into an object.

13 · State Behavioral

An order behaves differently depending on its lifecycle stage. Rather than one huge if (state == ...) block, model each state as its own object.

Created   → can cancel
Paid      → can refund
Shipped   → cannot cancel
Delivered → can review
🧠State = object behaves differently depending on its current state.

Factory vs Strategy vs Chain

A classic interview trap. The cleanest way to separate them:

PatternThe question it answersExample
FactoryWhich object should I create?PaymentFactory → creates CardPayment
StrategyWhich behavior / algorithm should I use?PaymentService → uses CardStrategy
ChainWho should handle this request?Manager → Director → VP → CEO
